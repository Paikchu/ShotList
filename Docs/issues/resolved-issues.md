### P0-4 · 打开镜头面板会自动修改并保存描述

**验证状态：** 模拟器实测

**代码位置：** ShotList/Views/ClipOptionsSheet.swift · .task / scheduleDraftSave / flushDraft

**预期结果：** 仅浏览或关闭面板不改描述和 JSON；真实输入仍自动保存，不回填猜测的原始描述。

**问题详情**

面板中的 `.task` 等待约 0.9 秒后，无条件追加「（探针追加）」。描述变化会触发自动保存；每次重新打开都会重复追加，污染原始描述、导出文件名和分镜指南。等待任务忽略取消错误，提前关闭也不能作为可靠保护。

**复现方法（修复前）**

1. 在测试数据中新建一个有描述的镜头。
2. 打开镜头面板，不做任何输入，等待约 1.5 秒后关闭。
3. 再次打开，检查描述及 shots.json：文本已被追加「（探针追加）」。重复打开会继续追加。

**修复状态：** 已修复

**修复说明：** 删除延迟追加描述的临时探针，取消后不再抢焦点，未编辑草稿不触发首尾空白裁剪。

**验证结果：** iOS 26.5 / iPhone 17 Pro Max，独立 bundle com.max.ShotList.DebugFixes：输入 Original note 后正常持久化；连续三次打开面板各等待超过 2 秒并关闭/重开，shots.json 字节与基线完全一致。Build iOS Apps 构建运行通过。

**修复 commit：** 3bbfc42c49f474368e4f806f82525b651752b34f

### P0-5 · 元数据读取失败后被当成空库，旧数据可能被覆盖

**验证状态：** 隔离存储测试及模拟器实测

**代码位置：** ShotList/Models/ShotStore.swift · load / applySnapshot / writeMetadata

**预期结果：** 无法读取记录时显示错误，禁止新增/改写/删除及孤儿清理；恢复有效记录后可重试，首次启动正常建库。

**问题详情**

`load` 用 `try?` 吞掉读取和解码错误，无法区分首次启动、暂时不可读和 JSON 损坏。失败后以空分镜列表计算孤儿文件，原素材会被列为「未使用文件」；新增操作还会覆盖原元数据。用户若继续清理，视频文件也会被删除。

**复现方法（修复前）**

1. 在隔离目录创建 ShotStore，添加一个镜头及一个片段。
2. 将该目录的 shots.json 改为无效 JSON，再用同一目录重新创建 ShotStore。
3. 观察结果：shots=0、orphans=1；原视频仍存在，却被当成未使用文件。
4. 新增一个镜头后检查 shots.json，原文件内容已被新列表覆盖。

**修复状态：** 已修复

**修复说明：** 区分首次启动与读取/解码失败；失败时阻止全部仓库写操作和孤儿清理，显示独立错误页及重新读取。元数据缺失但素材存在也进入保护状态。新增隔离目录单元测试和测试 scheme。

**验证结果：** Build iOS Apps test_sim：4/4 通过，覆盖损坏 JSON、元数据为目录、有素材但元数据缺失、首次启动及有效空库。损坏状态逐项调用增删改/排序/清理/视频保存均不覆盖原文件，恢复后可重读。iOS 26.5 模拟器实测错误页、失败重试保留原字节、恢复备份后回到原分镜。

**修复 commit：** 20ccc251fd885f09d9d624d06bd97f849c3eda28

### P0-6 · 元数据写入失败仍报告保存成功，重启后片段失去关联

**验证状态：** 隔离存储测试及模拟器实测

**代码位置：** ShotList/Models/ShotStore.swift · addClip / commit / persist / writeMetadata / syncClipFileNames

**预期结果：** 元数据提交失败必须向调用方报告错误，保留源视频和旧记录/文件；成功重试并重启后仍能找到新片段。

**问题详情**

保存流程先复制视频、删除源文件，再写入元数据。`writeMetadata` 忽略写入错误，因此 `addClip` 仍正常返回，界面会提示成功并退出回看。重启后新片段没有元数据引用，成为孤儿文件。重编号后的元数据提交失败也可能造成文件名与记录不一致。

**复现方法（修复前）**

1. 在隔离目录创建一个镜头及待保存的临时视频。
2. 把 shots.json 替换为同名目录，强制后续元数据写入失败。
3. 调用 addClip：方法无错误返回，源文件被删除，内存片段数为 1。
4. 重新创建 ShotStore，片段数变为 0；目标视频仍在磁盘，但已失去分镜关联。

**修复状态：** 已修复

**修复说明：** 元数据编码和原子写入改为抛错；仓库保存失败恢复已提交快照并清理本次新文件，源视频在成功提交后才删除。重编号先复制再提交、提交后清理旧文件，删除操作也后置到元数据成功之后。非 throwing 操作返回失败并显示内联提示；描述草稿失败时保留面板，完成/拍摄/导入/播放前检查保存结果。

**验证结果：** Build iOS Apps test_sim（iOS 26.5）：8/8 通过，其中新增写入失败重试、编码失败、增删改与重编号回滚、磁盘校正提交失败测试。模拟器实际相册导入在 shots.json 为目录时显示导入失败、源视频保留且无新增目标文件；恢复后再次导入成功，重新启动仍有关联。描述编辑失败保留草稿和面板，恢复后点击完成正常保存。相机回看使用同一 addClip 抛错路径并由现有 catch 保留 reviewURL；未执行真机录制及真实低空间测试。

**修复 commit：** ffcd00ce7ee1e4320be58d558797d933651d09ce

### P1-8 · 长按菜单清空片段未经确认直接删除

**修复状态：** 已修复

**修复说明：** 长按菜单改为 destructive 操作，仅设置待确认镜头；确认弹层说明数量、不可恢复及保留分镜，确认后才清空。

**验证结果：** iOS 26.5 独立 App：含两条真实测试视频的卡片长按清空后出现确认，JSON 和两文件保持；点击弹层外取消后卡片仍显示两条；再次长按并明确确认后两文件及片段引用删除，分镜 ID、描述和编号保留。构建运行通过。

### P1-9 · 空状态下分镜页整条导航栏的触摸被吞，右上角按钮点不动

**验证状态：** 模拟器实测

**代码位置：** ShotList/Views/ShotListView.swift · emptyState / toolbarContent（`ToolbarItem(placement: .largeTitle)`）

**预期结果：** 空状态下右上角的加号、三点与标题按钮与列表状态一样可点：加号弹出镜头面板，三点打开影片菜单，点标题弹出改名弹窗。

**问题详情**

分镜页的标题改名按钮挂在 `largeTitle` 位、占住整条标题行（该写法来自 d4a5c54，因为标签根页上的 `navigationTitle` 不是可点按钮）。当根页内容不是滚动容器时——空状态把 `ContentUnavailableView` 直接铺在根上——整条导航栏的触摸区域被吃掉：

- 在导航栏上真实触摸加号、三点，菜单与镜头面板都不出现，也不弹改名弹窗，即点击既没有到达目标按钮，也没有被标题按钮接走，没有任何反馈；
- 同一时刻内容区的「添加分镜」按钮正常，说明不是全局模态或整窗失效；
- 列表状态（有镜头）没有这个问题，因为那一份内容本身就是 `List`；空状态是任意一部没有镜头的影片，包括未命名影片、改名后的空影片，以及「重制」刚开出来的空白影片——也就是用户截图里那一屏。

定位依据（iOS 26.5 / iPhone 17 Pro Max，同一份数据下逐个变体实测，记录在探针日志中）：空状态改用 `ScrollView` 承载、或去掉标题按钮，导航栏触摸都立即恢复；只去掉背景、只去掉 `frame`、把标题按钮的 `maxWidth: .infinity` 去掉，仍然点不动。可见触发条件是「`largeTitle` 位的自定义标题按钮 + 根页非滚动内容」，与影片是否命名无关（有名 / 未命名的空影片表现一致）。

影响：空状态下加号、三点（切换影片 / 改标题 / 重制）与点标题改名全部不可用。加镜头还有内容区按钮可用，影片菜单要绕到历史页，因此定为 P1 而不是 P0。

**复现方法**

1. 在测试数据中准备一部**没有镜头**的影片（未命名或已命名均可），把它设为当前影片。
2. 进入「分镜」标签页，确认显示「这部影片还没有分镜」空状态、导航栏标题为该影片名。
3. 点击右上角加号：观察没有镜头面板出现、空状态也不变。
4. 点击右上角三点：观察影片菜单不弹出。
5. 点击导航栏标题：观察改名弹窗不出现。
6. 对照：切到任意有镜头的影片（列表状态），重复第 3–5 步，三个按钮均正常响应。

**修复状态：** 已修复

**修复说明：** 空状态改为与列表状态一致的写法——用 `ScrollView` 承载 `ContentUnavailableView`，并用 `containerRelativeFrame(.vertical)` 让它仍然占满一屏；配 `.scrollBounceBehavior(.basedOnSize)`，内容不满一屏时不回弹。根因（自定义标题按钮与非滚动根内容的相互作用）不改动标题按钮本身，避免影响「点标题改名」这条既有设计。

**验证结果：** iOS 26.5 / iPhone 17 Pro Max，App 真实安装后由 XCUITest 探针按下真实触摸（探针工程放在 /tmp，不进入仓库）：修复前，未命名空影片与有名空影片的空状态下点加号、三点均无任何反应（菜单 / 面板 / 改名弹窗都不出现）；修复后，两条空影片用例的加号均弹出镜头面板、三点均打开影片菜单、点标题弹出「影片标题」改名弹窗，有镜头的列表状态用例无回归。空状态上滑位移为 0（不出现回弹）。版式与改前逐像素比对，差异像素数 0（阈值 12，1320×2868）。构建运行通过。

**修复 commit：** 69dcd1cbeb338be44063061c3d45faccb18035c4

### P2-16 · 导出过程中素材缺失会重新编号，片段序号与界面不一致

**验证状态：** 隔离测试实测

**代码位置：** ShotList/Support/ExportPackageBuilder.swift · build / available.enumerated

**预期结果：** 缺失素材不改变其余片段的原始条号；文件名、CSV 和指南保持同一对应关系。

**问题详情**

界面按 `shot.clips` 的位置显示「第 N 条」，导出却先过滤磁盘上不存在的文件，再重新从 1 编号。正常前台校正已缩小触发范围，但导出取得快照后文件消失仍会触发，导致文件名、CSV 和指南的片段号与原界面不一致。

**复现方法（修复前）**

1. 准备一个含三条片段的镜头，记录界面的第 1、2、3 条及对应文件。
2. 在隔离测试中先取得 shots 快照，再删除第 1 条文件；不调用 refreshStorageStats。
3. 用该快照调用 ExportPackageBuilder.build。
4. 检查导出文件名及 CSV：原第 2 条被标成第 1 条，原第 3 条被标成第 2 条。

**修复状态：** 已修复

**修复说明：** 先按原 clips 数组枚举条号再过滤缺失文件；文件名、CSV 和指南使用原始条号及原总数，主素材从仍可用的片段中选择。

**验证结果：** Build iOS Apps test_sim：隔离目录实际打包四组数据（全量、第1条缺失、仅第3条、最新条缺失），验证目标文件字节、CSV 条号、指南主/备用路径与快照一致，全部通过。

**修复 commit：** 569643ead51b5b63bd3d679f3c77f19eaa9aaceb

### P2-17 · 导出缺少空间预检，空间不足时仅显示系统错误

**验证状态：** 隔离故障测试及模拟器实测

**代码位置：** ShotList/Support/ExportPackageBuilder.swift · build / zip

**预期结果：** 在复制前尽可能提示空间不足；导出过程中耗尽空间也给出可执行提示，清理失败产物并保留源素材。

**问题详情**

导出先复制素材，再生成和复制压缩包，需要额外临时空间；旧导出包可能也仍存在。流程没有检查可用空间，直到复制或打包失败才显示系统错误，没有说明空间不足及可采取的措施。实际峰值取决于复制和压缩行为，不能固定按素材大小估算。

**复现方法（修复前）**

1. 在专用测试设备或受限测试卷中准备较大素材，使剩余空间不足以完成导出。
2. 点击「生成导出包」。
3. 检查是否在复制/打包阶段才失败，且提示仅包含系统错误，没有明确的空间不足说明。

**修复状态：** 已修复

**修复说明：** 导出前估算素材工作副本、临时及最终 zip 与文本开销，读取重要用途可用容量并给出释放空间提示；容量未知时继续并保留运行时保护。保留 Cocoa/POSIX 及底层磁盘满错误类型，失败清理工作目录和不完整 zip。

**验证结果：** 隔离测试覆盖预检容量为0（复制次数0）、容量未知/充足、复制视频和复制zip时注入 ENOSPC、嵌套Cocoa错误及非空间错误，全部通过；源素材字节不变，失败无工作目录/残缺zip。模拟器独立测试App临时注入可用容量0，点击生成导出包显示预计空间/当前空间/释放空间提示，探针已移除。未填满真实设备磁盘。

**修复 commit：** 43e0a9c392b23541de39ab784497c623e87cd39d

### P2-37 · 缩放上限被硬编码为 8×，不随设备与格式变化

**验证状态：** 隔离单元测试；真机上的系统推荐区间未测

**问题详情**

界面可滑到哪由 `min(maxAvailableVideoZoomFactor, 8)` 决定，8 是应用自己拍的固定值，既不随设备变，也不随当前格式变，两头都会偏：

- 设备把镜头切换行为设为锁定或受限时，`minAvailableVideoZoomFactor` 会被抬到当前那颗镜头的换镜头倍率（见 AVCaptureDevice.h 中 `AVCapturePrimaryConstituentDeviceSwitchingBehaviorLocked` 的说明），`maxAvailableVideoZoomFactor` 同步收窄。界面仍按固定上限画档位与吸附点，会给出设备此刻到不了的倍率。
- 系统在 `activeFormat` 上提供 `systemRecommendedVideoZoomRange`，这正是内建相机缩放控件使用的区间，回答的是「该让用户滑到哪」。硬编码的 8× 会把这个推荐整个盖掉：推荐区间比 8× 窄时界面给出系统并不推荐的档位，比 8× 宽时又拿不到系统认为可用的区间。

**复现方法**

模拟器上不可复现：没有摄像头时 `configureIfNeeded` 先返回失败，取景页走降级分支，`refreshDeviceCapabilities` 与 `zoomScale(for:)` 都不执行。可用代码级验证：

1. 向 `ZoomRangePolicy.range` 传入推荐区间与可用区间，观察结算结果。`CaptureFramingTests` 已覆盖推荐更窄、推荐更宽、推荐为 nil、取交为空、可用上下界颠倒五种情形，以及区间收窄后档位随之减少。
2. 真机验证：进入取景页，换到可用范围被收窄的设备状态（如锁定镜头切换），观察焦距胶囊与吸附点是否仍停在固定上限上。

**修复状态：** 已修复

**修复说明：** 区间改由 `ZoomRangePolicy.range` 结算：优先取 `activeFormat.systemRecommendedVideoZoomRange`，并与 `minAvailable/maxAvailable` 取交集——不能直接采用推荐值，头文件写明可用区间会在推荐区间**之内**再被收窄，否则仍会给出到不了的档位。系统未提供推荐值时（该属性允许为 nil）退回「可用区间压到 8×」的老口径。取交为空、或设备上报的上下界颠倒时退回实际可用区间，避免 `ClosedRange` 越界构造崩溃。删除 CameraRecorder 中的固定上限常量，区间随格式变化重新结算（换分辨率/帧率与切前后摄都会走一次）。

### P2-39 · 镜头面板把没改过的编号也当成一次编辑写回，面板打开期间编号被重排后，只改描述也会把镜头挪回旧位置

**验证状态：** 模拟器实测（隔离测试数据 + 临时探针注入删除补偿）

**代码位置：** ShotList/Views/ClipOptionsSheet.swift · `draftNumber` 初始化、`flushDraft()`；ShotList/Models/ShotStore.swift · `update(_:)`、`recoverPendingDeletions()`（行号为修复前；修复后对应 `numberEdit` / `displayedNumber` / `flushDraft()`）

**问题详情**

**预期行为：** 用户只改了分镜描述（或字幕、角标），落盘就只改这三样文字，镜头在列表中的位置不动。

**实际行为：** `flushDraft()` 无条件把 `edited.number = clamped` 一起写回，`clamped` 来自 `@State draftNumber`——它在面板**打开的那一刻**由 `shot.number` 初始化，之后只有 Stepper 会更新它。因此只要面板打开期间这个镜头的编号被别的路径改过，用户接着敲一个字，`store.update(_:)` 就会按这个过期编号把镜头 `remove` + `insert` 回旧位置，并连带把它后面所有镜头重新编号、把磁盘上的片段文件改名。

**根因证据：**

- `ClipOptionsSheet.swift:62` `_draftNumber = State(initialValue: shot.number)`——`@State` 的初值只在视图身份建立时生效一次，面板打开后不会再跟随 `live.number`；
- `ClipOptionsSheet.swift:340-351` 的 guard 把「编号变了」和「文字变了」并成一个条件，任一命中就整条写回，其中包含 `edited.number = clamped`；
- `ShotStore.swift:427-431` 拿 `updated.number` 当目标位置做移动，不区分这个编号是用户改的还是过期快照。

**面板打开期间能改到编号的路径：** `ShotStore.commit()` 每次落盘都会调 `recoverPendingDeletions()`；一旦它真的找回过东西（`restored == true`），第 912–917 行会把**全部影片的全部镜头**按下标重新编号，`mergeRecovered` 还可能在中间插回一条整镜（第 967 行），使当前镜头的编号整体后移。此时面板里的 `draftNumber` 已经过期。触发前提是此前有过「JSON 已提交、文件没删成功」的残留日志，因此触发窗口窄，定为 P2 而不是 P1；但根因是「把未修改的字段也当成编辑写回」，与触发概率无关。

**同时澄清一项此前存疑的问题：** 「切换分镜顺序时分镜描述回填到别的镜头上」这一条，在当前代码里**不成立**。`flushDraft()` 是全应用唯一写 `note` / `caption` / `badgeText` 的地方（已按 `\.note = ` / `\.caption = ` / `\.badgeText = ` 全仓检索确认），它先取 `live = store.shot(withID: shot.id)` 再改字段，`ShotStore.update(_:)` 又按 `edited.id` 定位目标，两道都按 id 走，描述不会落到别的镜头上。拖拽排序、上移 / 下移、Stepper 改编号三条路都经 `normalize()` 按下标连续重编号，`update(_:)` 的「先摘后插」在上移与下移两个方向上的落点也都核对过（5 个镜头把第 2 个改成第 4 个 → 落在下标 3；把第 4 个改成第 2 个 → 落在下标 1），没有差一位。

**复现方法**

1. 隔离测试数据：新建一部影片，加 3 个镜头，都写上可区分的描述（A / B / C）。
2. 代码级验证（不破坏真实素材）：在 `ShotStore.recoverPendingDeletions()` 的 `if restored {` 分支入口临时插一条探针，确认进入该分支时会执行第 913–917 行的整库重编号。
3. 构造残留日志：用隔离目录的 `pending-deletions.json` 让恢复流程真的找回一条镜头（不要对用户真实的 Application Support 目录操作）。
4. 打开镜头 B 的面板，不动 Stepper，只在「分镜描述」里追加一个字，等 400 毫秒。
5. 观察分镜列表：镜头 B 被移回打开面板时的那个位置，后续镜头编号整体变化，磁盘上的片段文件名跟着改名。预期正确结果是只有 B 的描述变了，顺序不动。
6. 验证完成后移除全部探针与隔离数据。

**修复状态：** 已修复

**修复说明：** 根因是 `ClipOptionsSheet` 打开时把 `shot.number` 抄进 `@State draftNumber`，而 `flushDraft()` 把「编号变了」和「文字变了」并成一个条件、命中任一就整条写回（含编号），过期副本因此被当成一次用户编辑。修复把 `draftNumber` 换成只记录用户拨动的 `numberEdit: Int?`：没拨过（`nil`）时 `displayedNumber` 取 `live.number`，Stepper 与导出文件名预览都跟随仓库，`flushDraft()` 写回的编号就是仓库当前值，`ShotStore.update(_:)` 不会触发移动；拨过则夹进 `numberRange` 并按用户目标移动；落盘成功、或拨回与仓库一致后清回 `nil`，之后仓库编号再变也不会被旧编辑盖回；落盘失败保留用户拨的值，沿用原有重试行为。`ShotStore.update(_:)` 的移动语义不动，改动仅在 `ClipOptionsSheet.swift`。
