## 一、P0 — 必须先处理

- [x] **P0-2 · `load()` 把「读不到」当成「不存在」，一次启动就能把全部片段记录永久删掉（第二轮，已实测复现）**
  - 位置：`ShotList/Models/ShotStore.swift:327-348`（`load()`），关键在 337-343 的
    `fileManager.fileExists(atPath:)` 判定与 347 行的 `if didRepair { persist() }`
  - 现象：`fileExists` 对「文件确实不在」和「目录暂时读不到（权限 / 数据保护未解锁 /
    备份恢复中 / 目录创建失败）」返回的都是同一个 `false`。`load()` 不加区分地把这些片段
    从内存里剔掉，并且**立刻把结论写进 `shots.json`**。实测：把片段目录 `chmod 000`
    后启动一次，JSON 里的 5 条片段记录变成 0 条，而磁盘上 10 个视频文件一个不少——
    记录没了，文件还在，从此在应用里看不见、不计入占用空间、也不会被导出带走。
  - 为什么会这样：这条「校正立刻落盘」是上一轮 P2-4 的修法引入的。修 P2-4 之前
    `load()` 只改内存、不落盘，同样的误判要等下一次数据变更才写进 JSON；改成立刻落盘后，
    误判变成了「启动一次即生效、且不可逆」。
  - 修法：
    1. 用 `try fileManager.contentsOfDirectory(at:)` 是否抛错来区分「目录不可访问」与
       「目录可访问但文件不在」，**目录不可访问时直接跳过整段校正**（连编号都不要动）；
    2. 单个文件的存在性判定改用 `URL.resourceValues(forKeys: [.isRegularFileKey])` 的
       抛错语义，`EACCES` 一律按「未知」处理，不当作「不存在」；
    3. 剔除记录时留一份可恢复的副本（例如写 `shots.repaired.json`，或在日志/界面上告知），
       避免静默永久丢失。
  - 验收：重复上面的 `chmod 000` 实测——启动后 JSON 仍是 5 条；恢复权限后再启动，5 条完好。

- [x] **P0-1 · 临时验收钩子没删，且每次冷启动跑一次全量导出**
  - 位置：`ShotList/App/ShotListApp.swift:13-27`
  - 现象：`.task` 里每次启动都执行一次 `.everything` 完整导出（复制全部视频 → 打 zip）。代码注释自己写着「用完删掉」。一旦 `git add -A` 就会进仓库，装到真机上等于每次开 App 都白搬一遍全部素材。
  - 修法：删除该 `.task`，改为启动时清理上一次会话留在临时目录的导出包。
  - 验收：文件内不再出现 `TEMP_EXPORT_*` 字样；启动后临时目录不含上一轮的包。

- [x] **P0-3 · 工作区里又挂了一个 TEMP 导出钩子，只差一次 `git add -A` 就进仓库（第三轮，已处置）**
  - 位置：`ShotList/App/ShotListApp.swift:20-30`（相对 `HEAD` 多出来的那 12 行）
  - 现象：`git status` 里这个文件和 `project.pbxproj` 并排挂着「已修改」，但当时没人看它。
    工作区版本每次冷启动都会跑一次 `.everything` 全量导出，再 `print("TEMP_ZIP …")`，
    注释自己写着「TEMP 核对钩子……核对完删除」——是第二轮核对导出包内容时加上去的，
    核对完没删。和 P0-1 是同一件事，区别只在 P0-1 那份已经提交过、这条还躺在工作区：
    任何一次不带思考的 `git add -A` 就会把它带进仓库，装到真机上等于每次开 App 白搬一遍全部素材。
  - 处置：已删除这 12 行，`git diff --quiet -- ShotList/App/ShotListApp.swift` 通过
    （与 `HEAD` 一致），`grep -rn "TEMP_" ShotList/` 无输出。未提交，等本次清单一起提交。
  - 结论：P0-1 的修法本身是对的（`HEAD` 是干净的 27 行版本），问题出在**核对手法本身会留脏**。
    以后临时钩子一律加 `TEMP_` 前缀并当场删，交付前固定跑一次
    `grep -rn "TEMP_" ShotList/`（这轮就是靠它抓到的）。

## 二、P1 — 真 bug，可复现

- [x] **P1-1 · CSV 没有转义换行，一条记录被拆成两行**
  - 位置：`ShotList/Support/ExportPackageBuilder.swift:320-323`（`csvField`）
  - 现象：分镜描述用的是 `TextField(axis: .vertical)`，可以输入多行。`csvField` 只对 `,` 和 `"` 加引号，含换行的描述会直接把一行拆成两行，后面整列错位（实测 2 条数据输出 4 行），导出的 `分镜清单.csv` 在 Excel 里对不上号。
  - 修法：`\n` / `\r` 也走引号分支（标准 CSV 允许引号内含换行）。
  - 验收：多行描述的一条记录在 CSV 里仍只占一行，Excel / Numbers 打开列对齐。

- [x] **P1-2 · 「待拍」有两套互相矛盾的口径**
  - 位置：`ShotList/Models/ShotStore.swift:61`（`todayPendingCount`）vs `ShotList/Views/TodayView.swift:53,96,101`
  - 现象：标签栏徽标用「今天没拍」（`todayPendingCount`），今日页的「还没拍」统计块与「下一个 / 今天的分镜都拍完了」用「从没拍过」（`pendingShots`）。昨天把 3 个镜头全拍完、今天打开 App：徽标显示 `3`、进度环 `0%`、正文写着「今天已经拍了 0 个镜头」，旁边却打出绿色的「今天的分镜都拍完了」。
  - 修法：今日页的进度环、徽标、「下一个」提示统一取「今天还没拍」这一个口径，并把口径收进 `ShotStore` 作为唯一来源；统计块「还没拍」保留「从没拍过」的含义（它与「今日已拍」「往日已拍」构成三分，不能混）。
  - 验收：全拍完昨天的数据下，徽标、进度环、提示三者自洽，不再出现 0% 却「都拍完了」。

- [x] **P1-3 · `cleanUp()` 是死代码，临时目录只增不减**
  - 位置：`ShotList/Support/ExportPackageBuilder.swift:230-233`
  - 现象：全项目零调用。每个导出包体积≈全部视频，留在 `tmp/ShotListExport/` 里从不回收；一次会话里导出几次就堆几份全量体积。
  - 修法：启动时调一次 `cleanUp()`；另外每次生成新包后只保留最新一份 zip。
  - 验收：一次启动内连续导出两次，临时目录里只留 1 个 zip；重启后上一轮的包被清掉。

- [x] **P1-4 · 主素材有两个真相源，时间戳并列时互相打架**
  - 位置：`ShotList/Support/ExportPackageBuilder.swift:155,164,257,473`
  - 现象：写进根目录的那条由 `clip.id == latest.id` 决定；而清单 / 指南里的「主素材」由 `takeIndex != takeTotal` 反推。`max(by:)` 在时间戳完全相同时返回**第一个**最大值（已实测），于是两条路径立刻不一致——指南会把真正在根目录的那个文件列进「备用片段」，把备用片段写成「主素材文件」。
  - 修法：`ManifestRow` 直接存 `isMain`，由 `build()` 在落盘时传入，其余地方一律引用它；同时把「并列时取哪一条」定死为数组里靠后的一条（片段按拍摄先后追加，靠后的才是更晚拍的）。
  - 验收：时间戳完全并列的 3 条片段，指南里的「主素材文件」与实际在根目录的文件一致。

- [x] **P1-5 · 「今日已拍 / 往日已拍」两个统计块的数字与点击后的筛选结果对不上（第二轮，已实测截图）**
  - 位置：`ShotList/Views/TodayView.swift:118-135`（`statRow` 里两个已拍块都传 `filterTarget: .recorded`）
    ↔ `ShotList/Views/TodayView.swift:59-65`（`filteredShots` 的 `.recorded` = `store.shots.filter(\.hasClip)`）
  - 现象：两个块的数字各自只数**一个子集**（今日已拍 = `todayRecorded.count`，往日已拍 =
    `earlierRecorded.count`），但点下去都切到「已拍」这一个**并集**筛选。实测数据
    （镜头 01、02 今天拍过，03 是昨天拍的）：点「今日已拍 2」后列表列出 3 张卡片。
    与上一轮修掉的 P1-2 是同一族问题——数字与它指向的列表不是同一个口径。
  - 证据：`Docs/screenshots/审查-01-统计块数字与筛选结果对不上.png`（块上写 2，列表 3 条）
  - 修法：把筛选值拆到与统计块一一对应（`全部 / 今日 / 往日 / 未拍` 四段，或点块时切到对应的
    精确筛选），保证「点哪个块，列表就是那个块数的那些镜头」。
  - 验收：四段筛选各自的条数与同名的统计块数字相等。

- [x] **P1-6 · 录制中直接关掉相机：临时片段没人回收，音频会话可能停在播放态（第二轮，代码级）**
  - 位置：`ShotList/Views/CameraCaptureView.swift:111-147`（`topBar` 的关闭按钮在录制中没有被禁用）、
    `:57-62`（`onDisappear` 只 `recorder.stop()`，不处理 `reviewURL`）、`:465-477`（`enterReview`）、
    `ShotList/Camera/CameraRecorder.swift:192-218`（`completion` 一直留着，直到 `didFinishRecording` 才清）
  - 现象：录制中那个「✕」是可点的，点下去 → `dismiss()` → `onDisappear` 里 `recorder.stop()`
    让 AVFoundation 收尾 → 录制回调把 `completion` 交回主线程 → 已经被关掉的页面又执行一次
    `enterReview(url)`：把音频会话切成 `.playback` 并 `setActive(true)`。
    两个后果：
    1. 这段刚录好的 `tmp/shot-<uuid>.mov` **不会有任何人删**（只有「重拍」和「使用这条」两条
       出口会处理它），一直躺在临时目录里；
    2. `stop()` 在队列侧还会 `deactivateAudioSession()`，与上面那次 `setActive(true)`
       谁先谁后不确定——若 `enterReview` 后到，音频会话就停在 `.playback + active` 上，
       而唯一会归还焦点的 `onDisappear` 早就跑完了。
  - 影响面：`cleanUp()` 只清 `ShotListExport`（`ExportPackageBuilder.swift:238-241`），
    `tmp/shot-*.mov` 与相册导入失败时留下的 `tmp/import-*` 从来没有回收路径，
    只能靠系统清临时目录。
  - 修法：录制中禁用关闭按钮（或先 `stopRecording()` 再关）；`stop()` 里把 `completion`
    清空并删除它对应的临时文件；`cleanUp()` 扩成「清 `ShotListExport` + 清 `tmp/shot-*`、`tmp/import-*`」；
    `enterReview` 前加一道「页面还在不在」的判断。
  - 验收：真机录制中直接关相机 → 临时目录不残留 `shot-*.mov`，控制中心里的音频焦点正常归还。
    模拟器无摄像头，只做代码级核对。

## 三、P2 — 条件触发 / 隐患

- [x] **P2-1 · 相册导入一律改名为 `.mov`**
  - 位置：`ShotList/Support/MediaImport.swift:16`、`ShotList/Models/ShotStore.swift:238`（`addClip`）、`ShotList/Support/ExportPackageBuilder.swift:308`（`mainFileName`）
  - 问题：任何相册视频都落成 `import-<uuid>.mov`，接着 `addClip` 又把片段命名成 `.mov`，导出时 `mainFileName` 也写死 `.mov`——三处都在丢扩展名，mp4 被改名的同时容器没变，导出后交给剪映存在扩展名与容器不符的风险。
  - 修法：三处一起改成跟随源文件扩展名：导入保留原扩展名；片段命名与编号改名沿用原扩展名（`token` 与扩展名分开存）；导出命名取片段扩展名；编辑页的文件名预览读该镜头主素材的扩展名。
  - 验收：mp4 片段在库内、改名后、导出包里都仍是 `.mp4`。

- [x] **P2-2 · 从「设置」授权后回到 App，相机页仍停在旧状态**
  - 位置：`ShotList/Views/CameraCaptureView.swift:22`（`@State` 的 `authorization`）
  - 问题：`authorization` 只在 `.task` 与 `requestAccess()` 里更新；用户去系统设置里打开相机权限再切回来，界面还显示「权限已关闭」，必须关掉相机重进。
  - 修法：`scenePhase` 变为 `.active` 时调 `refreshAuthorization()` 重读权限，按新状态切到取景或对应的说明页。

- [x] **P2-3 · 播完片段不归还音频焦点**
  - 位置：`ShotList/Views/ClipPlayerScreen.swift:73-76`
  - 问题：切成 `.playback` 且 `setActive(true)` 后从不 `setActive(false)`，退出后别的 App 的音乐不恢复。
  - 修法：`onDisappear` 里 `setActive(false, options: .notifyOthersOnDeactivation)`。

- [x] **P2-4 · 读取时校正了编号却不落盘，极端情况下片段会「凭空消失」**
  - 位置：`ShotList/Models/ShotStore.swift:285`（`load()`）
  - 问题：`load()` 会过滤已消失的文件、并调 `normalize()` 改名磁盘文件，但从不 `persist()`。磁盘文件名与 JSON 记录因此长期不一致，下次启动按「文件不存在」过滤就会把片段从界面上抹掉（文件其实还在磁盘上）。
  - 修法：`normalize()` 改为返回「是否改动过」，`load()` 里只要过滤掉了片段或重排过编号就立刻 `persist()`。

- [x] **P2-5 · 解析视频时长留在主线程**
  - 位置：`ShotList/Support/Haptics.swift:30`（`VideoMetadata.duration`）
  - 问题：默认主协程隔离下，裸的 `nonisolated async` 会留在调用方所在的主协程上，`AVURLAsset` 的构造与解析都压在主线程。同文件 `decodeThumbnail` 已经标了 `@concurrent`，这里漏了。
  - 修法：补 `@concurrent`。

- [x] **P2-6 · 视图 body 里做同步文件 I/O，且同一份计算做了两遍**
  - 位置：`ShotList/Models/ShotStore.swift`（`totalClipBytes`、`clipURL(for:)`、`clipURLs(for:)`）；`ShotList/Views/ExportView.swift:65,76`

| 行 | 内容 | 来源 | 判断 |
|---|---|---|---|
| 1 | 镜头 01 | 头部自己写的编号 | 与导航栏标题「镜头 01」重复 |
| 2 | 镜头 1 | `Shot.displayDetail` 对空描述的回退 | 与第 1 行几乎同形，看着像另一条数据 |
| 3 | 还没拍 | `statusCaption` 的未拍分支 | 缩略图位置本身就是虚线框加号 |

改法：

- 头部不再写编号——导航栏标题已经承担，同屏出现两次只是噪声；
- 描述为空时画虚线占位，与分镜卡片共用 `NotePlaceholder`（`DesignSystem.swift`）：
  同一道虚线在两处出现，长度与疏密不会各自漂移；
- 「还没拍」整行删除，只有拍过才写「已拍 N 段 · 共 X」；
- `displayDetail` 的空描述回退**保留**——导出、分享的 subject 需要一个名字，
  只是界面头部不再用它。改的是「谁在用」，不是那个回退本身。

## 十三、分镜描述内联进镜头面板（2026-09-15 02:30-02:55，用户实测反馈）

### 用户反馈

### 改动
- `ShotEditorView.swift` 整个删除，描述与编号编辑并入 `ClipOptionsSheet`：
  - 「分镜描述」一节：`TextField(axis: .vertical)` 直接改，`onChange` 防抖 0.5 秒自动落盘（`store.update`），退出面板也会即时保存；

  - 「顺序」一节：镜头编号步进器（原编辑页能力），改编号即改位置，磁盘文件名同步归一化；
