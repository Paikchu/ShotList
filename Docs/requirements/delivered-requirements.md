### R-4 · 用户停止录制后应当立刻看到回看画面，而不是先等界面卡一下

**验证状态：** 真机实测（iPhone 17 Pro Max、iOS 27.0、扬声器）：停止 → 回看不再冻结、重拍后录得到声音已验；蓝牙耳机、停止后立刻下拉关闭、10 分钟上限、保存后卡片时长未验，用户确认问题解决后关闭

**代码位置：** ShotList/Views/CameraCaptureView.swift · `content` / `showsCaptureLayer` / `enterReview` / `cancelReviewTasks` / `resolvedDuration`；ShotList/Camera/CameraRecorder.swift · `activatePlaybackAudioSession` / `releasePreviewLayer`；ShotList/Camera/CameraPreview.swift · `dismantleUIView`

**预期结果：** 点「停止」之后回看界面与第一帧立即出现，界面不出现卡顿；音频稍后接上开始播放。点「保存」之后回到取景（或关闭相机）同样没有可感知的等待。「回看 → 重拍」回到取景后仍然录得到声音。

**需求详情**

**当前行为：** 用户反馈每次停止录制都要等较长时间才能继续。停止到可继续拍摄之间串了三件事：

1. AVFoundation 收尾写文件（`movieOutput.stopRecording()` → `didFinishRecordingTo`），不在应用控制范围内；
2. `enterReview` 在**主线程同步**把音频会话从录制模式切到播放模式（`setCategory` + `setActive`）。这两个调用要等音频路由真的切过去才返回，期间主线程画不了任何东西；
3. 点「保存」之后才开始解析视频时长（`AVURLAsset` 加载），用户要为这一步再等一次。

**复测修正（2026-09-21）：** 第一版只处理了上面第 2、3 项，真机上仍卡顿（录约 2 秒、点停止后至少卡 3 秒）。用临时计时探针加主线程堆栈采样，在 iPhone 17 Pro Max / iOS 27.0（1080p30 HEVC，防抖 `.auto` 实际生效为 cinematicExtendedEnhanced）上逐段量出：

- 点「停止」到 AVFoundation 写完文件：356–510 ms，主线程空闲；
- `enterReview` 本身约 10 ms；音频会话切换（`setCategory` + `setActive`）扬声器下约 35–90 ms，且第一版已不在主线程——**它不是瓶颈**；
- **主线程被阻塞约 9.1 秒**（两次复现：9109 / 9094 ms），卡在回看界面替换取景界面时的 `CameraPreview.dismantleUIView` → `previewLayer.session = nil`。堆栈符号化为 `-[AVCaptureVideoPreviewLayer setSession:]` → `-[AVCaptureSession _commitConfigurationAndSkipWait:]` → `-[AVCaptureSession _buildAndRunGraph:skipWait:]` → `-[AVRunLoopCondition _waitInMode:untilDate:]`：摘预览层会触发一次会话配置提交，并在**调用线程**上同步等采集图重建完成。此时会话刚 `stopRunning()`；
- 同一个赋值在会话停下几秒之后几乎不花时间（4.7 秒后 18 ms，13 秒后 0 ms），耗时集中在「刚录完就摘」。

**目标行为：** 第 2、3 两件事，以及上面量出的预览层摘除，都不再占用「用户正在等」的那段时间。

- 音频会话切换挪到 `CameraRecorder.sessionQueue` 上异步执行，回看界面与播放器先立起来，切完再 `play()`；
- 时长解析提前到进入回看时就在后台开始，用户看回放的这段时间正好把它算完，点「保存」时直接取结果；
- 回看期间取景层不撤（回看盖在上面，取景层只是藏起来），预览层的最终摘除放到后台队列做，主线程不再等采集图重建。

**范围：** 仅相机取景页的「停止 → 回看 → 保存 / 重拍」这条路径。

**明确不做：**

- **不引入 iOS 27 的 ProVideoStorage。** 核对过 iOS 27.0 SDK 头文件（`AVProVideoStorage.h`、`AVCaptureFileOutput.h` 的 `usesProVideoStorage`）：它保的是高码率捕获**过程中**的写入吞吐确定性（面向 ProRes），不缩短停止时的收尾；而且容量由用户在系统设置里配、会随录制消耗、`busyReasons` 非空时启动录制直接失败。当前录制为 H.264/HEVC 且有 600MB / 10 分钟上限，够不上适用场景，引入它只会给主路径新增失败分支。等接入 ProRes 或长时间持续录制时再单独立项。
- **不改防抖模式。** `.auto` 在该机上选到 cinematicExtendedEnhanced，会裁切视野并增加延迟，是画质取舍，不属于本需求；需要时单独立项。
- **不改 `MediaFileCopy` 的落盘方式。** 曾假设 `ShotStore.addClip` 里那次 `temporaryCopy` 是全量字节拷贝、按文件大小收费，并据此改成硬链接。实测推翻：在 iOS Foundation 下对 600MB 文件调 `FileManager.copyItem`，耗时 0.000 秒、卷可用空间零增长——APFS 会做 COW 克隆，这一步本来就不按大小收费。改动已回退，`copyItem` 保留（克隆语义比硬链接更安全：硬链接会让源与目标共享同一个 inode）。

**对其他功能的影响：** 音频会话切到播放模式与 `resumeSession()` 里切回录制模式排在同一条串行队列上，先后顺序由调用顺序决定，「回看 → 重拍」不会出现播放模式后到、把录制模式盖掉导致回到取景录不到声音。

取景层在回看期间保留并隐藏（不透明度 0、不接触摸、对无障碍隐藏）：回看与重拍不再摘 / 重挂预览层，重拍回到取景不经过主线程上的预览层挂载。关闭相机时预览层在后台队列摘除，不阻塞关闭动画。回看盖住取景层时，若相机权限被收回或会话变为不可用，取景层随之撤下，回看画面仍保留，未保存的这一条不会因此丢失。

**验收方法**

1. 前置环境：真机安装 Debug 构建（模拟器没有摄像头，这条路径走不到），准备一部至少含 1 个镜头的影片，分别在外放和蓝牙耳机两种输出下各走一遍。
2. 进入取景页，录制约 10 秒，点「停止」。观察：回看界面与第一帧是否立即出现，中间有没有可感知的卡顿。
3. 在回看页立即点「保存」，确认回到取景（或关闭相机）没有可感知等待，且片段时长在分镜卡片上显示正确、非 0。
4. 重复第 2 步，这次在回看页点「重拍」，立刻再录一条并确认**录得到声音**（验证音频模式没有被播放模式盖住）。
5. 停止录制后立刻下拉关闭相机页，确认没有崩溃、没有残留 `shot-*.mov` 临时文件。
6. 录满 10 分钟上限让 AVFoundation 自动收尾，确认同样进入回看且时长正确。
7. 失败判据：停止后界面出现肉眼可见的冻结；重拍后录不到声音；保存后片段时长为空或为 0。

**实现状态：** 已交付

复测后的第二版：`CameraCaptureView.content` 改为取景层常驻（`showsCaptureLayer`）、回看叠在上面；预览层的最终摘除（`dismantleUIView`、`detachPreviewLayer`）统一走 `CameraRecorder.releasePreviewLayer`，在专用后台队列上执行，图层由闭包持有到摘完。

### R-6 · 用户点分镜页里还没拍的镜头的虚线加号时，应直接进入该镜头的拍摄，而不是先进镜头面板再点「拍摄」

**验证状态：** 模拟器实测；模拟器无法覆盖的项经用户验收通过（2026-09-21）

**代码位置：** ShotList/Views/ShotCardView.swift · `onCapture` / `captureAction` / `captureTarget`（虚线加号的独立点击层）与 `accessibilityActions`（自定义操作「拍摄」）；ShotList/Views/ClipThumbnailView.swift · `ThumbnailCaptureButtonStyle`；ShotList/Views/ShotListView.swift · `shotRow` 的 `onCapture`；ShotList/Views/HistoryView.swift · `card(for:)` 的 `onCapture` 与 `captureRequest`；复用 ShotList/Views/ShotFlowModifier.swift · `ShotCaptureRequest` / `startCapture`（R-11 已加，本条未改逻辑）

**预期结果：** 分镜页上，还没有片段的镜头，卡片左侧的虚线加号可以直接点：点一下就进入这个镜头的相机取景页，中间不经过镜头面板。卡片其余区域的点击行为不变，仍打开镜头面板。

**需求详情**

**当前行为：** 镜头还没拍时，卡片左侧缩略图位置是一个虚线框加号，视觉上就是「在这里加视频」的按钮；但点它与点卡片任何位置一样，只是打开镜头面板（`ClipOptionsSheet`），用户还要再点一次「拍摄」才进相机。一部影片有多个未拍镜头、逐个拍摄时，每个镜头都要多走「点卡片 → 等面板弹出 → 点拍摄 → 等面板收起」这几步。

**目标行为：**

1. 没有任何可用片段的镜头（判据与缩略图走到虚线加号那一支一致，即磁盘口径的「未拍」）上，虚线加号是一个独立的点击目标；点击后直接以该镜头进入相机取景页（效果等同镜头面板里点「拍摄」），并给一次 `Haptics.impact(.light)`。
2. 拍完（保存 / 关闭相机）回到分镜页，不经过镜头面板；该镜头卡片立即显示缩略图，虚线加号消失。相机页里既有的「从相册导入」入口照旧。
3. 卡片上加号以外的区域（描述、占位线、空白处）点击行为不变，仍打开镜头面板——写描述、导入、插入 / 复制仍走面板。
4. 已拍过的镜头没有加号，行为完全不变：点卡片仍打开镜头面板。
5. VoiceOver：卡片目前是一个合并的无障碍按钮（`accessibilityElement(children: .ignore)`），加号不会作为独立元素被读到。为未拍镜头增加一个自定义无障碍操作「拍摄」，效果与点加号一致；默认激活动作仍是打开镜头面板。已拍镜头不提供该操作。

**范围：** 分镜页（`ShotListView`）未拍镜头卡片上的虚线加号。

**推断（未经用户确认）：** 历史页的卡片（`HistoryView.card(for:)`）与分镜页共用 `ShotCardView` 和 `ShotFlowModifier`，「全部 / 未拍」筛选下同样会出现虚线加号。为避免同一个加号在两个标签页行为不一致，历史页同步生效；用户原话只提到分镜页，如只想改分镜页，需在实现前说明。

**明确不做：**

- 不改「新增分镜」（右上角加号、空状态按钮）的流程——新增仍是建一个空镜头并打开面板、光标落在描述框；本条只管**已存在的**未拍镜头上的那个加号。
- 不改相机页本身与导入流程；不在加号上加长按菜单或「拍摄 / 导入」二选一。
- 不做「拍完一条自动跳到下一个未拍镜头」，那是另一条需求。

**对其他功能的影响：**

- 整张卡片是一个 `Button`，加号要成为独立点击目标，就不能在它里面再嵌一个 `Button`（命中会被外层吞掉或双触发）。实现时需要把卡片改成「整卡点击区域 + 加号覆盖层」的结构，并确认长按 `contextMenu`、左滑删除、`onMove` 拖动排序都不受影响。
- 相机的 `fullScreenCover` 目前只有「面板 → 拍摄」能触发，需要给它增加一个从列表直接触发的入口，并沿用 `drainQueue` 的串行呈现约束，避免在别的弹层还没收起时弹相机。
- 镜头面板点「拍摄」前会先 `flushDraft()` 保存描述草稿；直接进相机没有草稿，不受影响。相机页对「描述为空」已有处理，未写描述的镜头也可以直接拍。
- 直接进相机后，「从相册导入」只剩相机页内的入口，或返回后点卡片其余区域走镜头面板。

**定级依据：** 由用户指定为 P1。「拍摄」是主路径，逐个拍未拍镜头时每个镜头都多一次面板往返；绕行方式是走镜头面板，但每个镜头都要多几步。

**验收方法**

1. 前置环境：真机安装 Debug 构建；模拟器没有摄像头，只能验证到「点加号 → 直接出现相机页」，录制、保存、回到分镜页要真机。准备一部含 4 个镜头的影片：镜头 1、2 未拍且描述为空，镜头 3 未拍且写过描述，镜头 4 已拍。
2. 进入「分镜」页，点镜头 1 的虚线加号：观察是否**直接**进入相机取景页，中间没有镜头面板弹出；取景页对应的是镜头 1。
3. 录一小段，点「保存」，再关闭相机：回到分镜页，镜头 1 卡片显示缩略图与时长，虚线加号消失；镜头面板没有出现。
4. 点镜头 2 卡片上加号以外的位置（描述占位线、卡片右侧空白）：确认仍是镜头面板弹出；在面板里点「拍摄」仍可正常进入相机。
5. 点镜头 3 的加号，确认取景页显示镜头 3 的描述；点镜头 4（已拍）的缩略图，确认打开镜头面板，行为与改动前一致。
6. 长按镜头 2 卡片弹出上下文菜单、左滑出现「删除」、拖动排序：三者仍可用，且不误触发相机。
7. 打开 VoiceOver，聚焦镜头 2：自定义操作里有「拍摄」，触发后进入相机；聚焦镜头 4：没有「拍摄」操作。
8. 切到「历史」页的「全部」筛选，点未拍镜头的加号，行为与分镜页一致。
9. 在系统设置里关闭本应用的相机权限后再点加号：走与「面板 → 拍摄」相同的权限说明页，不是无反应或崩溃。
10. 失败判据：点加号后仍先出现镜头面板；点卡片其余区域进了相机；已拍镜头的点击行为变化；相机关闭后停在镜头面板而不是分镜页；一次点击同时触发面板与相机。

### R-7 · 用户要让下一个分镜沿用上一个分镜的字幕与角标版式时，应能一步带过来再改，而不是重新敲一遍

**验证状态：** 模拟器实测（除下列未验证项）；VoiceOver 朗读为代码级确认

**代码位置：** ShotList/Views/ClipOptionsSheet.swift · `inheritableText` 与 `isBlank`（第 82–106 行）、「屏幕文字」一节里的「沿用上一镜」按钮（第 175–183 行）；ShotList/Models/Shot.swift · `trimmedCaption` / `hasCaption` / `trimmedBadgeText` / `hasBadgeText`（复用，未改）

**预期结果：** 在镜头面板的「屏幕文字」一节，点一下「沿用上一镜」就把上一镜的字幕和角标一起带到当前镜头，两个输入框立刻出现内容，用户只改变化的部分（比如把 62.5KG 改成 65KG）。只补当前还没写的那一项，已经写好的内容不会被覆盖。

**需求详情**

**当前行为：** 上一镜写了「辅助引体 ⌄ 62.5KG * 4 * 10」这样的字幕时，下一镜要把整句重新敲一遍，只为改一两个数字。面板里已经有「沿用上一镜」，但它只抄**角标**，字幕不在内；而且只有上一镜的角标非空、与当前角标不同时才出现，字幕这一半没有任何快捷入口。绕行方式是「在下方复制一个」（会连描述一起复制，还得回头改描述）或手敲。

**目标行为：**

1. 「沿用上一镜」改为一次带过来**字幕与角标两样**（合称「屏幕文字版式」）。不带描述、片段、编号——描述是「拍什么」，每镜不同，不属于版式。
2. **只补空项，不覆盖已写内容**：当前字幕为空才补字幕，当前角标为空才补角标；已写的那一项原样保留。
3. 出现条件：当前镜头不是影片里的第一个镜头；上一镜的字幕或角标至少有一项非空；并且至少有一项「上一镜有、当前为空」。三条有一条不满足就不出现（无可补时不显示一个点了没反应的按钮）。空白与否沿用全应用口径（`hasCaption` / `hasBadgeText`，去首尾空白后判断）。
4. 「上一镜」＝当前影片里编号排在前一位的镜头，与现有 `previousBadgeText` 一致，不是「上一个拍过的」；历史页的「未拍 / 已拍」筛选不影响它。每次取仓库里的最新值，不缓存。
5. **一次性拷贝，不联动**：带过来之后两镜的文字各自独立，改当前镜头不会反过来改上一镜。这是沿用现有原则——「留空」只有一种含义，即这一镜不出，不做「留空即沿用」这类隐式规则。
6. 带过来的文字进入现有草稿（`draftCaption` / `draftBadgeText`），走既有的 400 毫秒攒批落盘与关闭面板立即落盘，不另加保存动作。
7. 可以链式使用：镜头 3 沿用镜头 2（镜头 2 已经改过数字），镜头 2 沿用镜头 1。
8. 无障碍提示同步改成新说法（例如「把上一镜的字幕和角标抄过来，只补还没写的，抄完可以再改」），按钮文案保持「沿用上一镜」。

**范围：** 镜头面板（`ClipOptionsSheet`）。分镜页与历史页共用这个面板，两处同时生效。

**推断（未经用户确认）：**

- 用户说的「版式」按现有数据模型解读为字幕 + 角标这两段文字：位置、行数等真正的版式属性是影片级的（见「剪辑风格」），本来就对所有镜头生效；镜头级只有这两段文字。如果用户要的是别的东西（例如只要「有字幕」这个结构而不带文字，或连描述一起带），需在实现前说明。
- 覆盖规则选「只补空项」是为了不丢用户已经敲的字；代价是现有「沿用上一镜」能把一个已写的角标覆盖成上一镜的，改后要先清空再点。

**明确不做：**

- 不做分镜页长按菜单里的快捷入口：卡片上不显示字幕与角标，一步操作后在列表里看不到任何结果，只剩一次震动，用户无从确认。面板里两个输入框就在眼前，结果立刻可见。
- 不做占位符 / 模板变量（不自动把数字挖空）；不做「只抄字幕」「只抄角标」的分开按钮，不想要的那一项清掉即可；不做批量套用到多个镜头。
- 不新增数据字段，不改「在下方复制一个」与「在下方插入新镜头」的行为，不改导出。

**对其他功能的影响：**

- 现有「沿用上一镜」的行为变化：由「只抄角标、可覆盖已写的角标」变为「字幕与角标一起、只补空项」。实现说明里记录这一变化。
- 导出无影响：`分镜清单.csv`、`分镜文字内容指南.md` 读的仍是每个镜头自己的 `caption` / `badgeText`。

**定级依据：** 定为 P2（用户未指定级别，按规则判定，如需上调请说明）。不阻断从拍摄到导出的主路径，且有绕行方式：手敲，或用「在下方复制一个」带走文字再改描述；属于逐镜写字幕时的效率增强。

   字幕：<原字幕>

   - 不解析标签、不区分字段，AI 直接读文字。

**范围：** 镜头面板（分镜页与历史页共用）、`Shot` 模型与旧数据读取、导出包的 CSV 与指南、README 里的对应说法。

### R-3 · 用户在导出转码进行中改主意时，应当能直接停下这次导出

**验证状态：** 模拟器实测（除下列未验证项）；VoiceOver 朗读仅代码级确认

**代码位置：** ShotList/Views/ExportView.swift · `buildProgress`（进度 + 「停止」按钮）、`progressLabel`、`buildSection`；ShotList/Support/ExportSession.swift · `stop()`、`isStopping`、`build(_:isCurrent:builder:)` 的收尾分支、`publish(_:)`；未改动 ShotList/Support/ExportPackageBuilder.swift 与 ShotList/Support/MediaTranscode.swift（取消检查点与转码实现原样）

**预期结果：** 打包进行中，进度条旁边有一个「停止」入口；点它之后打包在下一段素材之前停下，界面回到可以重新选范围 / 格式的状态，临时目录里不留半成品。

**需求详情**

**当前行为：** 取消能力在底层已经完整实现——`ExportCancellation` 是原子标志，`build` 在每个镜头、每条片段与打包前都调 `run.checkCancellation()`，`ExportSession.invalidate()` 会置位它。但界面上没有任何入口调用 `invalidate()`：生成按钮在 `export.isBuilding` 时被禁用，进度区只有一条 `ProgressView` 和一行文字。唯一能触发取消的是去改「导出范围」或「视频格式」Picker（它们的 `onChange` 会调 `invalidate()`），这是副作用，不是取消，用户也不会知道。

选了「H.264 · 1080p」或「HEVC · 1080p」时每段素材要重编码，素材多时整个过程是分钟级；期间用户只能等，或退出应用。

**目标行为：**

1. `export.isBuilding` 为真时，在进度区右侧显示「停止」按钮，点击调 `export.invalidate()`。
2. 停止后不弹错误（取消不是失败——`ExportPackageBuilder` 已经把 `CancellationError` 与转码失败分开，见第 478 行），进度区收起，界面回到未生成状态。
3. 停止后不要显示「分镜、素材或导出范围已变化，请重新生成导出包」——那句话说的是另一回事；为「用户主动停止」给一句独立说明，或什么都不显示。
4. 确认临时目录里不留 `ShotListExport/<uuid>/`（`buildChecked` 的 `defer` 已经负责回收工作目录，验收时核对）。

**范围：** `ExportView` 加入口，`ExportSession` 按需要区分「被用户停止」与「输入变化作废」两种失效原因。

**明确不做：** 不做断点续传；不做后台继续导出；不改转码实现。

**对其他功能的影响：** `isStale` 目前一个布尔值同时表达两种失效原因，拆分时要确认 `build()` 完成后的 `guard generation == token, isCurrent()` 分支（ExportSession.swift:54–59）仍然把「迟到的结果」正确丢弃。

**定级依据：** 导出是主路径的最后一步，但默认档位「原片」不转码、耗时短，且用户可以退出应用终止，有绕行方式，因此定为 P2 而不是 P1。

**验收方法**

1. 前置环境：模拟器安装 Debug 构建，准备一部至少 6 个镜头都已拍、素材较大的测试影片（隔离数据）。
2. 在导出页把「视频格式」选为「H.264 · 1080p」，点「生成导出包」。
3. 等进度文字走到「正在转码 2 / 6 段」左右，点「停止」。
4. 观察：进度区在下一段素材开始前收起；不弹「导出失败」；「刚刚生成的导出包」一节不出现；界面上的范围 / 格式 Picker 与生成按钮恢复可用。
5. 用「文件」App 或调试命令检查应用临时目录，确认没有残留的 `ShotListExport/<uuid>/` 工作目录。
6. 再点一次「生成导出包」，确认能正常走完并产出可分享的包。
7. 失败判据：停止后弹出错误提示；或停止后进度仍继续推进到下一段；或临时目录留下工作目录。

**实现状态：** 已交付

**实现说明：** - **入口：** 打包进行中（`export.isBuilding`），打包一节的进度行右侧出现有边框的小按钮「停止」（列表行里的按钮必须用有边框样式，点击才只落在按钮上）。进度行在整个打包期间都显示：转码阶段是进度条 +「转码 N / M」；原片直接复制的阶段还没有进度可报，是一行转圈 +「打包中」，同样带「停止」。
- **不复用 `invalidate()`：** `ExportSession` 新增 `stop()` 与 `isStopping`，与输入变化的 `invalidate()` 分开。`stop()` 只置 `isStopping`、清进度、置取消信号；`build` 返回后看到 `isStopping`：丢掉这次产物（哪怕恰好已经打好），**不**置 `isStale`、**不**展示错误——取消被 `ExportPackageBuilder` 翻译成的 `打包失败：…` 文案也不展示，之前已经生成的包（若有）原样保留、仍然有效。用 `invalidate()` 会把已有的包标成「需重新打包」，那句话说的是另一回事。
- **输入变化优先：** 停止过程中如果又改了范围 / 格式，`generation` 已经变了，仍走原来的「输入已变化」分支（丢弃 + 标过期）；`build()` 的 `guard generation == token, isCurrent()` 迟到结果丢弃逻辑没有动。
- **「停止中」：** 取消信号只在下一段素材开始之前才被查看（转码实现不改），所以点了「停止」到打包真正停下之间可能还隔着当前那一段（实测 4K 素材转 1080p 每段约十几秒）。这段时间进度行改为「转圈 + 停止中」并收起按钮，免得点了没反应又点；`publish` 在 `isStopping` 时忽略在途的最后一次进度回传，进度条不会重新冒出来。
- **临时目录：** 没有改动，`buildChecked` 的 `defer` 本来就回收工作目录，验收时核对确实不留。
